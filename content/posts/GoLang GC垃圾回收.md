# 一、前言

垃圾回收（Carbage Collection，简称GC）是编程语言中提供的内存管理功能。

在传统的系统级编程语言（主要指C\C++）中，程序员定义了一个变量，就是在内存中开辟了一段相应的空间来存值。由于内存是有限的，所以当程序不再需要使用某个变量的时候，就需要销毁该对象并释放其占用的内存资源，好重新利用这段空间，在C\C++中，释放无用变量内存的事情需要程序员自己来处理，就是说当程序员认为变量没用了，就手动释放其占用的内存。但是这样显示非常繁琐，如果有所遗漏，就可能造成资源浪费甚至内存泄漏。当软件系统比较复杂，变量多的时候程序员往往就忘记释放内存或者在不该释放的时候释放内存。这段程序员开发人员是一个比较头痛的问题。

为了解决这个问题，后来开发出来的几乎所有新语言（java、 python、 php 等）都引入了语言层面的自动内存管理 - 也就是语言的使用者只需要关注内存的申请而不需要关注内存的释放，内存释放由虚拟机（virtual machine）或运行时（runtime）来自动进行管理。而这种不再使用的内存资源进行自动回收的功能就被称为垃圾回收。

因为GC 是一个复杂而且庞大的体系，本文核心角度深入浅出。

<br/>

# 二、GC 回收的是什么

在应用程序中会使用到两种内存，分别是堆（Heap） 和 栈（Stack），GC 负责回收堆内存，而不负责回收栈中的内存。那么这是为什么呢？

主要原因是栈是一块专用内存，专门为了函数执行而准备的，存储着函数中的局部变量以及调用栈。除此之外，栈中的数据都有一个特点 -- 简单。比如局部变量不能被函数外访问，所以这块内存用完直接释放掉。正是因为这个特点，栈中的数据可以通过简单的编译器指令自动清理，并不需要通过 GC 来回收。

<br/>

# 三、内存垃圾的回收

程序在内存上被分为 堆区、栈区、全局数据区、代码段、数据区 五个部分。对于 C++ 等早期编程语言栈上的内存由编译器回收，堆上的内存空间需要编程人员负责申请与释放。在 Go 中栈上内存仍有编译器负责管理回收，而堆上的内存由编译器和垃圾收集器负责管理回收，给编程人员带来了极大的便利性。

![mem-stack](https://img1.kiosk007.top/static/images/blog/20250828001446-mem-stack.png)

垃圾是指程序向堆栈申请的内存空间，随着程序的运行已经不再使用已经不再使用这些内存空间，这时如果不释放他们就会造成垃圾也就是内存泄漏。

<br/>

## 数据在内存中存放的原则

（1）一个证书类型内部

低地址存储低位，高地址存储高位。比如 int a = 1，则存储情况为 0000 (高地址) 0000 0000 0001 (低地址) 。

（2）若干个局部变量（在栈中存储）

先定义的高地址，后定义的低地址。

（3）类、结构体或数组的元素

先定义的低地址，后定义的高地址。

例如下面这段程序：

```go
package main

type Person struct {
    phone *Phone
}

type Phone struct {
    money int 
}

func main() {
    ming := new(Person)
    
    // 一开始使用的是 XiaoMi
    xiaomi := &Phone{money: 2999}
    ming.phone = xiaomi
    
    // iPhone 出了新款，换一部
    iphone := &Phone{money: 5999}
    ming.phone = iphone
}
```

xiaoming 随着他的手机从 小米换成了苹果，`phone` 所指向的`xiaomi`内存空间变成了垃圾，需要对其进行回收，否则就变成了内存泄漏。

## 指针和内存分配

什么是内存变量？

每当我们编写任何程序时，我们都需要在内存中存储一些数据/信息。数据存储在特定的存储器中。内存地址看起来像 `0xAFFFF` (这是内存地址的十六进制表示)。

现在，要访问数据，我们需要知道存储它的地址，我们可以跟踪存储与程序相关的数据的所有内存地址。但想象一下，记住所有内存地址并使用它们访问数据会非常困难。这就是为什么引入变量。

变量是一种占位符，用于引用计算机的内存地址。

什么是指针？

指针是存储另一个变量的内存地址的变量。所以指针也是一种变量，只不过它是一种特殊变量，它的值存放的是另一个变量的内存地址。

## Go 类型占用内存情况

unsafe 包可以获取变量的内存使用情况

Go 语言提供以下基本数字类型：

无符号整数 uint8、uint16、uint32、uint64

整数符号 int8、int16、int32、int64

实数 float32、float64

整数（依赖操作系统类型、跟系统有关）uint、int、uintptr（指针）

- 32 位系统:  uint=uint32、int=int32、uintptr 为 32 位的指针
- 64 位系统：uint=uint64、int=int64、uintptr 为 64 位的指针

```go
package main

import (
	"fmt"
	"unsafe"
)

func main() {
	var uint8Value uint8
	var uint16Value uint16
	var uint32Value uint32
	var uint64Value uint64
	var int8Value int8
	var int16Value int16
	var int32Value int32
	var int64Value int64

	var float32Value float32
	var float64Value float64
	
	fmt.Println("uint8Value = Size:", unsafe.Sizeof(uint8Value)) // uint8Value = Size: 1
	fmt.Println("uint16Value = Size:", unsafe.Sizeof(uint16Value)) // uint16Value = Size: 2
	fmt.Println("uint32Value = Size:", unsafe.Sizeof(uint32Value)) // uint32Value = Size: 4
	fmt.Println("uint64Value = Size:", unsafe.Sizeof(uint64Value)) // uint64Value = Size: 8
	
	fmt.Println("int8Value = Size:", unsafe.Sizeof(int8Value)) // int8Value = Size: 1
	fmt.Println("int16Value = Size:", unsafe.Sizeof(int16Value)) // int16Value = Size: 2
	fmt.Println("int32Value = Size:", unsafe.Sizeof(int32Value)) // int32Value = Size: 4
	fmt.Println("int64Value = Size:", unsafe.Sizeof(int64Value)) // int64Value = Size: 8
	
	fmt.Println("float32Value = Size:", unsafe.Sizeof(float32Value)) // float32Value = Size: 4
	fmt.Println("float64Value = Size:", unsafe.Sizeof(float64Value)) // float64Value = Size: 8
}
```

以上的是基本类型，接下来了解复杂类型，以结构体类型为例：

```go
type Example struct {
    BoolValue bool 
    IntValue  int64
    FloatValue float32
}
```

该类型代表复杂类型，它代表 7 个字节，带有三个不同的数字表示。bool 表示1个字节，int16 表示2个字节，float32 增加 4个字节，但是，在此结构的内存中实际分配了8个字节。

所有内存都分配在对其边界上，以最大限度地减少内存碎片整理。要确定对齐边界 Go 用于自定义结构体，可以运行 `unsafe.Alignof` 函数。Go 为 64bit Darwin 平台的对齐边界是 8 个字节。因此，当 Go 确定结构的内存分配时，它将填充字节以确保最终内存占用量是 8 的倍数，编译器将确定添加填充的位置。

**什么是内存对齐呢？**

内存对齐，也叫边界对齐（boundary alignment），是处理器为了提高处理性能而对存取数据的起始地址所提出的一种要求。编译器为了使我们编写的 C 程序更有效，就必须最大限度地满足处理器对边界对齐的要求。

计算机体系结构通常要求不同类型的数据在内存中的起始地址必须是某个特定值的整数倍。这个特定值被称为对齐边界，而按照这个规则进行数据存储的过程被称为内存对齐。对齐的好处包括提高数据访问的速度和优化内存使用。

- 参考 [CPU Cache Line](https://mecha-mind.medium.com/demystifying-cpu-caches-with-examples-810534628d71)

**用一句话通俗的说就是：所谓内存对齐就是让数据在内存中存储时占用内存的大小（字节数）是按照一定值的整数倍去存储。**



![mem-gc-3](https://img1.kiosk007.top/static/images/blog/20250828231609-mem-gc-3.png)

从处理器的角度来看，需要尽可能减少堆内存的访问次数以实现对数据结构进行更加高效的操作。

为什么？

这里有2个原因：

- **主要原因一：CPU 访问效率**

现代 CPU 访问内存时，并非一个字节一个字节地读写，而是以一个固定的块（block）为单位，这个块的大小就是 **“总线宽度”**。例如，一个 32 位系统可能以 4 字节为单位访问，一个 64 位系统通常以 8 字节为单位。

如果一个数据结构（比如一个 `int`）的起始地址是总线宽度的倍数（比如 4 字节或 8 字节的倍数），那么 CPU 只需要一个内存操作就能将其完整地读入寄存器。

**非对齐的后果：**

如果数据没有对齐，它的起始地址可能跨越两个总线块。在这种情况下，CPU 需要进行两次内存操作才能完整地读取这个数据：

1. 读取第一个块，得到数据的一部分。
2. 读取第二个块，得到数据的另一部分。
3. 然后 CPU 动用额外的逻辑将这两部分拼接起来。

这个过程不仅需要**额外的内存访问**，还会消耗**额外的 CPU 周期**来处理，从而显著降低性能。

- **主要原因二：CPU 缓存和 False Cache Line Sharing**

CPU 缓存的存取单位是**缓存行（Cache Line）**，通常为 64 字节。当 CPU 从内存读取数据时，会一次性将整个缓存行读入缓存。

- **如果数据结构对齐了，** 它可以完整地被一个或多个缓存行包含，而不会跨越缓存行的边界。这样，当一个线程访问这个结构时，它只会操作特定的缓存行。
- **如果数据结构没有对齐，** 它可能会跨越缓存行。更糟糕的是，如果它是一个大型的结构体，其中包含多个小变量，那么这些小变量很可能会被分配到同一个缓存行中。

这就是 **False Cache Line Sharing** 发生的基础。当两个或多个线程独立地修改这个结构体中不相关的变量时，由于这些变量共享同一个缓存行，CPU 就会为了维护缓存一致性而频繁地使其他核心的缓存失效。

# 四、GC触发条件

**Go 的自动垃圾回收的触发条件有两条**

1. 超过内存大小的阈值
2. 达到定时时间阈值是由一个 `gcpercent` 的变量控制的，当分配的内存占已在使用中的内存的比例超过 `gcprecent` 的时候就会触发，比如一次回收完毕后，内存的使用量为 5M，那么下次回收的时机则是内存分配达到 10M 的时候。也就是并不是内存分配的越多，垃圾回收的频率越高。如果一直达不到内存大小的阈值呢？这个时候就会被定时触发，比如一直达不到 10M，那就定时（默认 2min 触发一次）触发一次 GC 保证资源的回收。

# 五、垃圾回收算法

## 1. 引用计数 (reference counting)

引用计数通过在对象上增加自己被引用的次数，被其他对象引用时加 1， 引用自己的对象被回收时减 1，引用数为 0 的对象既可以被回收的对象。这种算法在内存紧张和实时性比较高的系统中使用的比较广泛，如 php、python 等。

优点：

1. 方式简单，回收速度快

缺点：

1. 需要额外的空间存放计数
2. 无法处理循环引用（如 a.b = b; b.a=a 这种情况）
3. 频繁更新引用计数降低了性能。

<br/>

## 2. 标记-清除 (mark and sweep)

该方法分为两步，标记从根变量开始迭代得遍历所有被引用的对象，对能够通过应用遍历访问盗的对象都进行标记为 “被引用“，标记完成后进行清除操作，对没有标记过的内存进行回收（回收同时可能伴有碎片整理操作）。这种方法解决了引用计数的不足。但是也有比较明显的问题，每次启动垃圾回收都会暂停所有的正常代码执行，回收时系统的响应能力大大降低！当然后续也出现了很多 mark & sweep 算法的变种（如三色标记法）就优化了这个问题。

<br/>

## 3. 复制收集

复制收集的方式只需要对对象进行一次扫描，准备一个 「新的空间」，从根开始，对对象进行扫描，如果存在对这个对象的引用，就把它复制到 「新的空间」 ，一次扫描结束之后，所有存在于 「新的空间」 的对象就是所有的非垃圾对象。

这两种方式各有千秋，标记清楚的方式节省内存但是两次扫描需要更多的时间，对于垃圾比例比较小的情况比较占优势，特别的，复制收集有「局部性」的优点。

在复制收集的过程中，会按照对象被引用的顺序将对象复制到新空间中，于是，关系较近的对象被放在距离较近的内存空间的可能性会提高，这叫做局部性，局部性的情况下，内存缓存会更有效地运行，程序的性能会提高。

对于标记清除，有一种标记-压缩算法的衍生算法。

对于压缩阶段，它的工作就是移动所有的可达对象到堆内存的同一个区域中，使他们紧凑的排列在一起，从而将所有的非可达对象释放出来的空闲内存都集中在一起，通过这样的方式来达到减少内存碎片的目的。

<br/>

## 4. 分代收集 (generation)

这种收集方式用了程序的一种特性，大部分对象会从产生开始在很短的时间内变成垃圾，而存在的很长时间的对象往往有较长的生命周期。

根据对象的存活周期不同将内存划分为新生代和老年代，存活周期短的为新生代，存活周期长的为老年代。这样就可以根据每块内存的特点采用最适当的收集算法。

<br/>

## 5. 三色标记法

- 白色对象 - 潜在的垃圾，其内存可能会被垃圾回收器回收；
- 黑色对象 - 活跃的对象，包括不存在任何引用外部指针以及从根对象可达的对象，垃圾回收器不会扫描这些对象的子对象；
- 灰色对象 - 活跃的对象，因为存在指向白色对象的外部指针，垃圾收集器会扫描这些对象的子对象；

三色表计算法是对标记阶段的改进，原理如下：

1. 起初所有对象都是白色。
2. 从根出发扫描所有可达对象，将其引用对象标记为灰色放入队列。
3. 从队列取出灰色对象，将其引用对象标记为灰色放入队列，自身标记为黑色。
4. 重复 3， 直到灰色对象队列为空。此时白色对象即为垃圾，进行回收。

三色标记的一个明显的好处是能够让用户程序和mark并发的进行，具体可以参考论文：[《On-the-fly garbage collection: an exercise in cooperation.》](https://dl.acm.org/doi/pdf/10.1145/359642.359655)

根集合：

- 全局变量：程序在编译期就能确定的那些存在与程序整个生命周期的变量。
- 执行栈：每个 goroutine 都包含自己的执行栈，这些执行栈上包含栈上的变量及指向分配的堆内存区块的指针。
- 寄存器：寄存器的值可能表示一个指针，参与计算的这些指针可能指向某些赋值器分配的堆内存的区块。



这里先说明一下：Go 以 STW 为界限，可以将 GC 划为五个阶段：

| 阶段              | 说明                                                       | 状态 |

| Sweep Termination | 清扫终止阶段，为下一个阶段的并发标记做准备工作，启动写屏障 | STW  |

## 1. GO 1.3 之前的标记 - 清除（mark and sweep）算法

此算法主要有两个主要的步骤：

- 标记（Mark phase）
- 清除（Sweep phase）

第一步：暂停程序业务逻辑，找出不可达的对象，然后做上标记。

第二步：回收标记好的对象。

操作非常简单，但是有一点需要额外注意：mark and sweep 算法在执行的时候，需要程序暂停！即 STW（stop the world）。也就是说，这段时间程序会卡在那里。

![mem-gc](https://img1.kiosk007.top/static/images/blog/20250901095457-mem-gc.png)



这里需要注意的所谓的“程序”，则是一些对象的跟节点的集合。

缺点：

- STW， stop the world 让程序暂停，程序出现卡顿。
- 标记需要扫描整个 heap。
- 清除数据会产生 heap 碎片。

![mem-gc2](https://img1.kiosk007.top/static/images/blog/20250901100156-mem-gc2.png)

## 2. Go 1.5 的三色标记法

三色标记法：实际上就是通过三个阶段的标记来确定清除的对象都有哪些。

根集合是 GC 在标记过程中最先检查的对象，主要包括：

- 全局对象：在程序编译期间就能确定，全局变量存在于程序的整个生命周期。
- 执行栈：Go 语言中协程是分配在堆上，每个协程都有自己的执行栈。
- 寄存器：寄存器的值可能表示一个指针，这些指针可能指向另一块内存空间。

**第一步**: 就是只要是新创建的对象，默认的颜色都是标记为 “白色“。

![mem-gc4](https://img1.kiosk007.top/static/images/blog/20250901101230-mem-gc4.png)



**第二步**：每次GC 回收开始，然后从根节点开始遍历所有对象，把遍历到的对象从白色集合放到“灰色”集合。

![mem-gc5](https://img1.kiosk007.top/static/images/blog/20250901101424-mem-gc5.png)

**第三步**：遍历灰色集合，将灰色集合的对象引用的对象从白色集合放入到灰色集合，之后将此灰色对象放入到黑色集合。

![mem-gc6](https://img1.kiosk007.top/static/images/blog/20250901101656-mem-gc6.png)

**第四步**: 重复第三步，直到灰色中无任何对象。

![mem-gc7](https://img1.kiosk007.top/static/images/blog/20250901101922-mem-gc7.png)

## 3. 没有 STW 的三色标记法

我们还是基于上述的三色标记法来说，它是一定需要依赖 STW 的，因为如果不暂停程序，程序的逻辑改变对象的引用关系，这种动作如果在标记阶段做了修改，会影响标记结果的正确性。

如果三色标记法，标记过程不使用 STW 将会发生什么事情？

![mem-gc8](https://img1.kiosk007.top/static/images/blog/20250901230916-mem-gc8.png)



对象 G 被清理掉，在调用时会出现空指针，程序异常。

当然，如果上述中的白色对象 G ，如果他还有很多下游对象的话，也会一并被清理掉。

在三色标记法中，以下情况时不希望发生的：

- 条件1：一个白色对象被黑色对象引用（白色被挂在黑色下面）
- 条件2：灰色对象与它之间的可达关系的白色对象遭到破坏（灰色同时丢了该白色）

为了防止这种现象的发生，最简单的方式就是 STW ，直接禁止掉其他用户程序对对象引用关系的干扰，但是 STW 的过程有明显的资源浪费，对所有的用户程序都有很大影响。如何能在保证对象不丢失的情况下合理的尽可能的提高 GC 效率，减少 STW 时间呢？

答案就是：**使用屏障机制，破坏上面的两个条件就可以。**

## 4. 屏障机制

**写屏障**：该屏障之间的写操作和之后的写操作相比，先被系统其他组件感知。就是在每一轮 GC 开始时会初始化一个叫做 “屏障” 的东西，然后由它记录第一次 scan 时，各个对象的状态，以便和第二次 re-scan 进行对比，引用状态变化的对象被标记为灰色以防丢失，将屏障前后状态未变化的对象继续处理。

让 GC 回收器，满足以下两种情况之一时，可保对象不丢失，所以引出两种方式。

### 4.1 “强-弱” 三色不变式

- **强三色不变式**

不存在黑色对象引用到白色对象

![mem-gc9](https://img1.kiosk007.top/static/images/blog/20250901233942-mem-gc9.png)

- **弱三色不变式**

所有被黑色对象引用的白色对象都处于灰色的保护状态。

![mem-gc10](https://img1.kiosk007.top/static/images/blog/20250901234554-mem-gc10.png)



黑色对象可以引用白色对象，白色对象存在其他灰色对象对他的引用，或者可达他的链路上存在灰色对象。

为了遵循上述两种方式，Go 通过两种屏障方式 “**插入写屏障**”、“**删除写屏障**” 进行实现



<br/>

**强三色不变式和弱三色不变式只要满足其中一条，就能保证 GC 的正确性。**



Go 语言在不同版本中采用了不同的写屏障技术，从最初的 Dijkstra 写屏障（满足强三色不变式）到后来的混合写屏障（**满足弱三色不变式**）。

目前的 Go GC（从 1.8 之后）采用的**混合写屏障就是为了满足弱三色不变式**。它在 GC 标记阶段，只在**堆上创建新对象或修改指针时**，将新指针指向的对象标记为灰色，从而保证了即使出现“黑指向白”，这个白色对象也一定能被后续的扫描发现，最终被标记，避免被误回收。(也就是说被废弃的对象会逃过一轮GC)

<br/>

### 4.2 插入写屏障

具体操作：在 A 对象引用 B 对象的时候， B 对象被标记为灰色。（将 B 挂在 A 下游， B 必须被标记为灰色）。

满足：强三色不变式。（不存在黑色对象引用白色对象的情况， 因为白色会强制变成灰色）。

我们知道黑色对象的内存槽有两种位置，栈和堆。插入屏障是一个很耗费性能的行为，栈空间的特点是容量小，但是要求相应的速度快，因为函数调用弹出平凡使用，所以 “插入屏障” 机制在栈空间的对象中不使用，而仅仅是使用在堆空间的对象操作中。



当通过几轮染色过程后：

![mem-gc11](https://img1.kiosk007.top/static/images/blog/20250902002624-mem-gc11.png)

在原来的基础上内存块划分了栈和堆内存，经过几次的标记之后，栈内存中的对象和堆内存中的对象的 对象E 已经被标记为黑色，对象 A 添加了新引用对象 D， 由于在栈中没有启用写屏障，所以对象 D 依然被标记为白色；对象 E 添加新引用对象 J，由于在堆中启动了写屏障，所以对象 J 会被标记为灰色。

正常继续使用三色标记法，最终结果可用得到对象K 和 对象D 会被清理，其余对象得到保留，这种结果显然不是我们想要的，因为栈中的对象D 被对象 A 所引用，不能被清理掉。

结果会是：

其实，GC 在准备清理白色标记的对象前， 会重新遍历扫描一次栈空间，这时需要加 STW 保护栈，具体的操作是：

在 GC 清理前，把 **栈对象** 全部标记为白色。然后对栈对象加 STW 保护，不允许在栈中创建或删除对象：

![mem-gc13](https://img1.kiosk007.top/static/images/blog/20250902003630-mem-gc13.png)

最终可以得到预期的结果了。

![mem-gc14](https://img1.kiosk007.top/static/images/blog/20250902003955-mem-gc14.png)

最终再清理掉标记为白色的对象。



**总结**：GC 中添加了写屏障机制可以极大地减少了 STW 时间，只是需要再结束时启动 STW 来重新扫描栈。GoLang 在使用三色标记法之前是采用标记-清除法来清理内存的，其需要在堆和栈同时添加 STW 保护，而使用了三色标记法和写屏障机制后，可以在回收堆对象时不使用 STW，只是在栈中使用，但栈的对象数目少，STW 的时间也不会太长。

### 4.3 删除写屏障

场景1：A 对象删除 B 对象的引用，那么 B 对象被 A 对象删除，B 对象被标记为灰色。

场景2：A 对象更换下游对象由 B 变成 C，B 对象被 A 对象删除，B 对象被标记会为灰色。

程序创建之初，所有的对象都被标记为白色。

![mem-gc15](https://img1.kiosk007.top/static/images/blog/20250902101115-mem-gc15.png)

经过遍历 RootSet 之后，对象 A 和 对象 E 被标记为灰色。

![mem-gc16](https://img1.kiosk007.top/static/images/blog/20250902101212-mem-gc16.png)

当程序运行时，对象 A 准备删除对象 D 。

![mem-gc17](https://img1.kiosk007.top/static/images/blog/20250902101348-mem-gc17.png)

此时触发删除写屏障，被删除的对象 D 被标记为灰色。



![mem-gc18](https://img1.kiosk007.top/static/images/blog/20250902101457-mem-gc18.png)

一轮 GC 过后得到的结果。

![mem-gc19](https://img1.kiosk007.top/static/images/blog/20250902101704-mem-gc19.png)





看到的最终结果可能不是大家希望的，对象 D 已经被对象 A 删除了，为啥 GC 不把它清理呢？

其实这样做是为了满足弱三色不变式原则，被删除对象都需要标记为灰色，假如对象 E 此时添加了对象 D 的引用，那么对象 E 就会被无辜的删除了，那么对象 D 什么时候被删除呢？

答案是等到下一轮 GC ，对象 A 肯定达不到对象 D ，同时也没有从 根节点出发的对象指向 D ，那么这个时候，对象 D 就会被合法的删除。

此时，我们可以看到删除写屏障的不足，回收精度低，一个对象即便被删除了，也依然可以活过一轮GC，在下一轮GC 才会被清除。

### 4.4 Go 1.8 混合(hybird write barrier)机制

**插入写屏障** 和 **删除写屏障**的 短板：

- 插入写屏障：结束时需要 STW 来重新扫描栈空间，标记栈上引用的白色对象的存活。

- 删除写屏障：回收精度低，GC 开始时 STW 扫描堆栈来记录初始快照，这个过程会保护开始时刻的所有存活对象。

Go 1.8 版本引入了 混合写屏障机制（hybird write barrier），避免了对栈 re-scan 的过程，极大地减少了 STW 的时间，结合了两者的优势。



#### 4.4.1 混合写屏障规则

具体操作：

1. GC 开始将栈上的对象全部扫描并标记为黑色（之后不再进行二次重复扫描，无需 STW）
2. GC 期间，任何在栈上创建的新对象，均为黑色。
3. 被删除的对象标记为灰色。
4. 被添加的对象标记为灰色。

满足：变形的弱三色不变式。

```bash
添加下游对象(当前下游对象 solt， 新下游对象 ptr) {
	// 1
	标记灰色(当前下游对象的slot)
	// 2 
	标记灰色(新下游对象ptr)
	// 3
    当前下游对象slot = 新下游对象ptr
}
```



补充：有了写屏障 GC 还是会停止业务，在启动屏障的时候会暂停业务一小会。

# 七、GC 的优化

在理解优化思路之前，我们先快速回顾一下 Go GC 的基本原理。Go 的垃圾回收器是一种**并发的、三色的标记-清扫（Mark-Sweep）**收集器。

它的主要特点是：

- **并发**：GC 运行时，大部分工作可以与你的应用程序 Goroutine 并行执行。
- **三色标记**：GC 将对象分为三类：
  - **白色**：未被标记的对象，初始状态下所有对象都是白色的。
  - **灰色**：已标记但其内部引用未被扫描的对象。
  - **黑色**：已标记且其内部引用已扫描的对象。
- **STW (Stop-The-World) 阶段**：GC 在某些关键时刻（如标记开始和标记结束时）会短暂地暂停所有应用程序 Goroutine。虽然这个暂停时间很短，但在高并发场景下，仍然可能对延迟造成影响。

GC 的目标是**尽可能减少 STW 时间，并让 GC 任务与程序并发执行**，从而降低对应用程序性能的影响。

------



## Go GC 优化核心思路



Go GC 的优化思路主要集中在**减少 GC 的工作量**，从而让 GC 能够更快地完成任务，减少对程序的影响。这不像其他语言那样需要手动管理内存，而是通过一些编程实践来**帮助 GC 更好地工作**。



1. **减少内存分配（首要原则）**

这是最重要的优化思路。Go GC 的工作量与**新分配的内存大小**直接相关。你分配的内存越多，GC 需要扫描和清理的工作量就越大。

- **使用对象池（`sync.Pool`）**：对于需要频繁创建和销毁的临时对象，使用对象池可以复用它们，避免重复分配。这对于像 HTTP 请求处理、JSON 解码等场景特别有效。
- **预分配切片容量**：当你创建一个切片时，如果知道其大致容量，应使用 `make([]T, 0, capacity)` 预分配。这样可以避免在切片增长时反复进行内存重新分配和数据拷贝。
- **复用内存**：避免在循环中创建新的对象，尽量复用已有的对象。例如，在处理大量数据时，可以考虑使用单个缓冲区，而不是每次循环都创建新的。

<br/>

2. **减少指针数量**

Go GC 是基于对象可达性的。GC 扫描堆上的对象时，需要遍历对象内部的指针，以确定其引用的其他对象是否为“活”的。**指针越多，GC 扫描的工作量就越大。**

- **避免大量小对象**：当你有很多小对象时，每个对象都有自己的元数据和可能的指针，这会增加 GC 的扫描开销。
- **善用值类型**：在切片或结构体中，如果可能，使用值类型（如 `int`, `float64`, `struct`）而不是指针。例如，`[]MyStruct` 比 `[]*MyStruct` 对 GC 更友好。

<br/>

3. **控制内存使用峰值**

如果你的程序内存使用量在短时间内出现剧烈波动，会迫使 GC 更频繁地运行。

- **监控和分析**：使用 Go 内置的 `pprof` 工具来分析内存分配情况，找出内存分配的热点，这能让你知道哪里是 GC 的主要工作来源。
- **调整 `GOGC` 环境变量**：`GOGC` 控制 GC 触发的时机。默认值是 `100`，表示当新分配的内存达到上一次 GC 内存的 100% 时触发。你可以根据需要调整它，但通常不建议随意修改，除非你对程序的内存行为有深入了解。

<br/>

4. **优化 GC 时间**

如果你的程序对延迟非常敏感，且 GC 时间是瓶颈，可以考虑以下方法：

- **调整 GC 触发时机**：如果你的程序允许较高的内存占用，可以适当调高 `GOGC` 的值，减少 GC 的频率。
- **避免在关键路径上分配内存**：在高并发、对延迟要求极高的代码路径上，尽量减少内存分配，将分配工作移到不那么敏感的地方。

<br/>



# 八、GC 的速度赶不上制造垃圾的速度

GC 的速度赶不上制造垃圾的速度，是一种典型的 **"内存泄漏"** 或 **"内存饥饿"** 场景。

在这种情况下，程序分配新对象的速率远远超过垃圾回收器回收无用对象的速率。这会导致以下几个关键问题：

## 1. 内存持续增长，直至耗尽



这是最直接的后果。由于 GC 无法及时清理垃圾，堆上的内存会持续累积。程序将不断向操作系统申请更多的内存来满足新的分配请求，直到物理内存或操作系统设定的内存上限被完全耗尽。

最终，程序会因为无法分配新的内存而崩溃，操作系统也可能因为内存不足而变得不稳定。

## 2. GC 频繁运行，性能下降



为了应对不断增长的内存，GC 会更频繁地触发。每次 GC 运行时，即使 Go 的 GC 已经高度优化，仍会有短暂的“**STW (Stop-The-World)**”阶段。GC 越频繁，这些短暂的停顿就越密集，导致程序的吞吐量和响应速度明显下降。

整个系统会陷入一种恶性循环：为了清理内存而频繁 GC -> GC 导致性能下降 -> 性能下降导致处理请求变慢 -> 积压的请求继续制造更多垃圾。

## 3. 应用程序“假死”或响应延迟



在高并发的 Web 服务中，如果 GC 陷入“饥饿”状态，用户会直接感受到服务响应变慢，甚至出现“假死”现象。一个原本只需要几毫秒完成的请求，可能因为 GC 的频繁运行而需要数十甚至数百毫秒才能完成，用户体验会变得非常差。

# 九、GC 的分析工具

GC 的分析和性能调优工具主要集中在 Go 语言内置的 `pprof` 工具链上。`pprof` 不仅能分析 CPU 和内存，还能专门用于深入研究 GC 的行为。

下面是分析 Go GC 的几个主要工具和方法：

## 1. go tool pprof

`go tool pprof` 是最核心的性能分析工具。通过它，你可以生成 GC 相关的火焰图、堆栈图和文本报告，从而直观地看到程序在哪些地方分配了大量内存，以及哪些对象正在占用内存。

- **如何使用？**

  1. **在代码中启用 `pprof` HTTP 服务**：

     Go

     ```
     import _ "net/http/pprof"
     import "net/http"
     
     func main() {
         go func() {
             http.ListenAndServe("localhost:6060", nil)
         }()
         // ... Your application code
     }
     ```

  2. **获取 GC 相关的堆（Heap）分析数据**： 在程序运行时，通过 `curl` 或 `wget` 获取堆内存的 profile 文件。

     Bash

     ```
     curl http://localhost:6060/debug/pprof/heap > heap.prof
     ```

  3. **使用 `go tool pprof` 分析**： 使用 `pprof` 命令行工具打开这个文件。

     Bash

     ```
     go tool pprof heap.prof
     ```

     进入 `pprof` 交互界面后，你可以使用以下命令：

     - `top`：按内存占用大小列出最耗内存的函数。
     - `list <function_name>`：查看特定函数的代码，找出内存分配的具体行。
     - `web`：生成 SVG 格式的火焰图，直观地展示内存分配的调用栈，方便你找到“热点”。

## 2. go tool trace



`go tool trace` 提供了更详细的、基于时间线的 GC 事件可视化。它能让你看到 GC 暂停（STW）发生的时间点、GC 运行时 Goroutine 的调度情况，以及 GC 的具体工作流程。

- **如何使用？**

  1. **在代码中启用追踪**：

     Go

     ```
     import "runtime/trace"
     import "os"
     
     func main() {
         f, _ := os.Create("trace.out")
         defer f.Close()
         trace.Start(f)
         defer trace.Stop()
         // ... Your application code
     }
     ```

  2. **运行程序**，生成 `trace.out` 文件。

  3. **使用 `go tool trace` 分析**：

     Bash

     ```
     go tool trace trace.out
     ```

     这会启动一个本地 Web 服务，你可以通过浏览器访问。在界面中，你可以看到一个时间轴，上面会标记 GC 事件，如“GC start”、“STW”等，帮助你分析 GC 导致的延迟。

## 3. runtime/debug 包



`runtime/debug` 包提供了一些函数，让你可以在代码中动态获取 GC 的信息，或者手动控制 GC 的行为。

- **`debug.ReadGCStats(&stats)`**： 这个函数可以获取详细的 GC 统计信息，如 GC 运行次数、总耗时等。你可以在程序中定期调用它，将数据记录到日志或监控系统中，以便于长期观察 GC 行为的变化。
- **`debug.FreeOSMemory()`**： 这个函数会强制 Go 运行时返回更多的内存给操作系统。在某些情况下，当你的程序内存使用量急剧下降后，Go 不会立即将内存还给 OS，而 `FreeOSMemory` 可以强制执行这个操作。

通过综合使用这些工具，你可以系统性地分析 Go 程序的 GC 问题，从宏观的时间线（`trace`）到微观的内存分配热点（`pprof`），最终找出并解决性能瓶颈。race

在 Go 中存在一些 与 GC 相关的 API：
