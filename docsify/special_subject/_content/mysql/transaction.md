# 事务

## 事务的隔离级别
四个隔离级别如下：

- **读未提交**，指一个事务还没提交时，它做的变更就能被其他事务看到；
- **读提交**，指一个事务提交之后，它做的变更才能被其他事务看到；
- **可重复读**，指一个事务执行过程中看到的数据，一直跟这个事务启动时看到的数据是一致的，MySQL InnoDB 引擎的默认隔离级别；
- **串行化**；会对记录加上读写锁，在多个事务对这条记录进行读写操作时，如果发生了读写冲突的时候，后访问的事务必须等前一个事务执行完成，才能继续执行；

## 什么是幻读

**幻读**是指在一个事务中，**前后两次查询同一个范围的数据，但第二次查询的结果集多出了或少了一些第一次查询没有的行**。这些新增或删除的行就像“幻影”一样，在两次查询之间“出现”或“消失”了。

**区别于不可重复读**： 不可重复读是指两次查询同一条**记录**，但记录的值发生了变化。幻读是指两次查询的记录集合发生了变化（增删）。

### 什么情况下会出现幻读

在 MySQL 的 **`REPEATABLE READ` (可重复读)** 隔离级别下，幻读是有可能发生的，特别是在执行 `SELECT ... FOR UPDATE` 或 `SELECT ... LOCK IN SHARE MODE` 这种 **当前读 (Current Read)** 操作时，或者在**不加锁的普通 SELECT (快照读 Snapshot Read)** 操作中，如果并发事务进行了 `INSERT` 或 `DELETE` 操作，并突破了 MVCC（多版本并发控制）的保护范围。

最经典的幻读场景发生在 `INSERT` 操作，并且当查询操作试图“锁定”一个范围时。



**为什么会发生？**

在 `REPEATABLE READ` 级别下，MySQL 的 **MVCC (多版本并发控制)** 机制可以防止**快照读 (Snapshot Read)** 产生幻读。然而，当事务进行**当前读 (Current Read)** 操作（例如 `SELECT ... FOR UPDATE` 或 `SELECT ... LOCK IN SHARE MODE`）时，它们需要读取最新的数据，而不是事务启动时的快照。



### MySQL 如何避免幻读 (Solutions in MySQL)

MySQL 的 InnoDB 存储引擎在 `REPEATABLE READ` 隔离级别下，通过一种称为 **Next-Key Locks (间隙锁 + 记录锁)** 的机制，很大程度上避免了幻读。

- Next-Key Locks 的作用：
  - **记录锁 (Record Locks)：** 锁定索引上的具体记录。
  - **间隙锁 (Gap Locks)：** 锁定索引之间的“间隙”，防止其他事务在这个间隙中插入新的记录。
  - **Next-Key Lock：** 是记录锁和它前面间隙锁的组合，锁定一个范围，防止该范围内的数据被修改或插入新数据。

**需要注意的是：**

- **Next-Key Locks 只在特定的情况下生效**：它主要作用于**索引**。如果查询的字段没有索引，或者查询无法利用索引（例如，全表扫描），那么间隙锁可能无法生效，幻读仍然可能发生。
- **非索引字段的幻读：** 如果 `category` 字段上没有索引，那么 `SELECT * FROM products WHERE category = 'Electronics' FOR UPDATE;` 可能会导致**全表扫描**，并对所有扫描到的行加上行锁。但间隙锁无法作用于没有索引的字段，这时并发插入新的满足条件的行仍然可能导致幻读。
- **快照读 (Snapshot Read) 不会出现幻读（在 RR 隔离级别）：** MySQL 的 `SELECT` 语句（不加 `FOR UPDATE` 或 `LOCK IN SHARE MODE`）是快照读。在 `REPEATABLE READ` 隔离级别下，快照读会基于事务启动时的 MVCC 快照，因此即使有新的行插入，快照读也不会“看到”这些新行，从而避免了幻读。幻读主要出现在**当前读**操作中。

## MVCC 的实现

**MVCC (Multi-Version Concurrency Control)**，中文叫**多版本并发控制**。它的核心思想是：**在数据库的读操作不加锁，而是通过保存数据在某个时间点的多个历史版本，让读操作可以读取数据的一个“快照”，从而实现读写操作的无冲突并发。**

简单来说，当一个事务正在修改数据时，另一个事务仍然可以读取到这个数据修改之前的版本，而不需要等待写事务完成。这样就大大提高了数据库的并发性能。

### MVCC 的实现原理：快照、版本链与 Read View

InnoDB 实现 MVCC 主要依赖以下几个核心组件和机制：

#### 1. 隐藏列（Hidden Columns）

InnoDB 会为每行数据（Record）添加一些隐藏的列，这些列是 MVCC 实现的基础：

- **DB_TRX_ID (6字节)**：表示**最近一次修改（INSERT/UPDATE）该行的事务 ID**。如果是 INSERT 操作，就是插入行的事务 ID；如果是 UPDATE 操作，就是执行 UPDATE 的事务 ID。
- **DB_ROLL_PTR (7字节)**：**回滚指针 (Roll Pointer)**。指向写入**回滚段（Undo Log）**的某个版本数据。通过这个指针，可以找到该行数据的前一个版本。
- **DB_ROW_ID (6字节)**：**隐藏的行 ID**。如果表没有定义主键，InnoDB 会自动为每行生成一个隐藏的 6 字节的行 ID，作为聚簇索引的一部分。

#### 2. Undo Log（回滚日志）

**Undo Log 是 MVCC 的“多版本”实现的关键。** 每当事务对数据进行修改（INSERT/UPDATE/DELETE）时，InnoDB 不会直接覆盖旧数据，而是会将旧数据的版本信息写入到 Undo Log 中。

- INSERT 操作的 Undo Log：
  - 当插入一行时，Undo Log 中会记录如何删除这行（逻辑删除）。
- DELETE 操作的 Undo Log：
  - 当删除一行时，Undo Log 中会记录这行的完整旧版本数据，并标记为删除。逻辑上，该行并非真正从数据页中删除，只是被标记为“不可见”，实际删除会在后续的 Purge 线程中进行。
- UPDATE 操作的 Undo Log：
  - UPDATE 操作最为复杂，它实际上是**先写入一个新版本的数据行，然后把旧版本的数据写入 Undo Log**。
  - 这个旧版本数据会通过 `DB_ROLL_PTR` 指针指向 Undo Log 中的上一个版本数据，从而形成一个**版本链（Version Chain）**。

#### 3. 版本链（Version Chain）

通过 `DB_ROLL_PTR` 和 Undo Log，每一行数据实际上都维护着一个由旧版本数据组成的链条。最新的数据行版本位于数据页上，而更早的版本则存储在 Undo Log 中。

- 当一行数据被多次更新时，就会在 Undo Log 中形成一个由 `DB_ROLL_PTR` 连接起来的**版本链**。
- 每个版本都会记录其对应的 `DB_TRX_ID`。

#### 4. Read View（一致性视图）

**Read View 是 MVCC 的核心，它决定了当前事务能够看到哪个版本的数据。** 当一个事务启动时（或者在 `REPEATABLE READ` 隔离级别下，第一次进行快照读时），InnoDB 会生成一个 `Read View`。

`Read View` 主要包含以下几个重要信息：

- **`m_ids` (Min-Max ID Set)：** 当前系统中**活跃的（未提交）事务 ID 列表**。
- **`min_trx_id` (Minimum Transaction ID)：** `m_ids` 列表中最小的事务 ID。
- **`max_trx_id` (Maximum Transaction ID)：** 系统中将要分配给下一个新事务的 ID（比当前已分配的最大 ID 大 1）。
- **`creator_trx_id` (Creator Transaction ID)：** 创建这个 `Read View` 的事务的 ID。

## 补充

MySQL 中非常重要的两个概念：**当前读 (Current Read)** 和 **快照读（Snapshot Read）**。理解它们对于把握 MySQL 的并发控制和事务隔离机制至关重要。

------

### 快照读 (Snapshot Read)：你看到的是历史版本

**快照读，顾名思义，就是读取某个时间点的“数据快照”。** 在 MySQL 的 InnoDB 存储引擎中，这是**默认的读取方式**，也是大多数普通 `SELECT` 语句的执行方式。

- **工作原理：**
  - 当你启动一个事务，并且执行一个普通的 `SELECT` 语句时，InnoDB 会为你创建一个该事务开始时的 **一致性视图 （Consistent Read View）**。
  - 这个视图就像一个时间戳，告诉你：“好，从现在开始，你看到的任何数据，都必须是你在我创建这个视图那一刻就已经存在并提交了的。”
  - 即使有其他事务在你之后修改了数据，或者插入了新数据，你的快照读也不会看到那些变化。你看到的是这个事务开始时数据的“旧版本”，也就是一个“快照”。
- **特点：**
  - **非锁定读 (Non-locking Read)：** 快照读不会对数据加任何锁。这意味着它不会阻塞其他事务的读写操作，大大提高了并发性。
  - **利用 MVCC (多版本并发控制)：** 快照读之所以能看到历史版本，正是因为它依赖于 MVCC。InnoDB 会为每一行数据保存多个版本，每个版本都有自己的事务 ID 和回滚指针。通过这些信息，MVCC 能够判断哪个版本的数据是当前事务可见的。
  - **可能滞后：** 因为看到的是历史快照，所以你读到的数据可能不是数据库中最新提交的数据。
  - 默认隔离级别（可重复读）下的表现：
    - 在 `REPEATABLE READ` 隔离级别下，一个事务中的所有快照读，都会使用**该事务第一次进行快照读时创建的那个一致性视图**。这意味着，在整个事务的生命周期内，你多次执行同一个 `SELECT` 语句，结果都是一样的（避免了不可重复读和幻读——因为你看不到新插入的行）。

- **应用场景：** 大部分的数据查询，只需要读取数据而不需要立即对其进行修改的场景。例如，生成报表、数据分析、用户浏览商品列表等。

### 当前读 (Current Read)：你看到的是最新版本

**当前读，顾名思义，就是读取数据库中“最新的已提交”的数据。** 它不像快照读那样看到历史版本，而是直接读取数据行当前的最新状态。

- **工作原理：**

  - 为了确保读到的是最新数据，并且在后续操作中保证数据的一致性，当前读通常会**对数据加锁**。
  - 锁定的目的是防止其他事务在当前事务读取并处理数据期间对这些数据进行修改，从而保证数据的一致性。

- **特点：**

  - 锁定读 (Locking Read)：

     当前读会对读取的数据加共享锁 (S锁) 或排他锁 (X锁)。

    - **共享锁 (S锁)：** 允许其他事务读取，但不允许修改。用于 `SELECT ... LOCK IN SHARE MODE`。
    - **排他锁 (X锁)：** 阻止其他事务的任何读写操作。用于 `SELECT ... FOR UPDATE`。

  - **总是读取最新数据：** 无论事务何时启动，当前读总是会获取数据的最新已提交版本。

  - **可能阻塞其他事务：** 因为要加锁，所以当前读可能会阻塞其他事务对被锁定数据的访问，影响并发性。

  - **解决幻读的关键：** 在 `REPEATABLE READ` 隔离级别下，正是通过当前读配合 **Next-Key Locks（间隙锁+记录锁）** 来避免幻读。当进行范围查询的当前读时，MySQL 会锁定查询范围内的所有现有记录以及这些记录之间的间隙，从而阻止其他事务在该范围内插入新数据，有效防止了幻读。

- **应用场景：** 当你需要读取数据并立即对其进行修改，或者需要确保你读取的数据是最新的，并且在你的事务完成修改之前不会被其他事务更改时。例如，银行转账时需要确保账户余额是当前的最新值，然后进行扣款；订单系统在创建订单前检查库存等。
