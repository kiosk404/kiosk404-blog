# 基础

## B+ 树和 B 树的比较

B 树和 B+ 都是通过多叉树的方式，会将树的高度变矮，所以这两个数据结构非常适合检索存于磁盘中的数据。

### B+树的优势

[访问 B+ 树可视化页面](https://www.cs.usfca.edu/~galles/visualization/BPlusTree.html)

MySQL（特别是 InnoDB 存储引擎）选择 B+ 树作为索引结构，是基于其在**磁盘存储系统**上的卓越性能。

1. **高效的磁盘 I/O**
    - **高扇出，降低树高：** B+ 树的内部节点**只存储键和指针**，不存储实际数据。这使得每个节点（通常为一个磁盘页）能容纳更多索引条目，从而**大大减少树的高度**。更低的树高意味着查找任何数据所需的**磁盘 I/O 次数更少**，这是提升数据库性能的关键。
    - **页式存储与局部性：** 节点大小与磁盘页（如 16KB）匹配，一次 I/O 就能加载整个节点。相关数据（相邻键）通常存储在同一个或相邻的磁盘页，符合**局部性原理**，提高了缓存命中率。

2. **稳定的查询性能**
    - **所有数据在叶子节点：** B+ 树的所有数据记录都只存储在**叶子节点**上。
    - **叶子节点同层：** 所有叶子节点位于树的**同一层级**。这确保了从根节点到任何数据记录的查找路径长度都相同，因此**查询时间复杂度稳定**，性能可预测。

3. **出色的范围查询和顺序访问**
    - **叶子节点链表连接：** B+ 树的叶子节点通过**链表**（在 InnoDB 中通常是双向链表）有序连接。
    - **高效遍历：** 这种结构使得**范围查询**（如 WHERE price BETWEEN 10 AND 50 ）极其高效。一旦找到范围的起始点，只需沿着叶子节点链表顺序遍历即可获取所有数据，无需频繁回溯父节点。这对于数据库中常见的范围查询和全表扫描至关重要。

**总结来说，B+ 树通过优化磁盘 I/O、确保查询性能稳定以及高效支持范围查询，成为最适合关系型数据库索引的数据结构。**

### B树的劣势
[访问 B 树可视化页面](https://www.cs.usfca.edu/~galles/visualization/BTree.html)

相较于 B+ 树，B 树（B-tree）的缺点主要体现在其在**磁盘存储和数据库索引**场景下的性能和适用性方面：

1. **磁盘 I/O 次数通常更多**
    * **内部节点存储数据：** B 树的内部节点（非叶子节点）除了存储键外，还可能存储实际的数据记录（或指向数据记录的指针）。这意味着在给定相同的磁盘页大小下，一个 B 树的内部节点能容纳的键数量会**更少**。
    * **树的高度更高：** 内部节点能容纳的键少，导致其“扇出”（fan-out）较低，从而使得 B 树的**整体高度通常会比同等数据量的 B+ 树更高**。树的高度越高，查找任何一条记录所需的**磁盘 I/O 次数就越多**，这是数据库性能的主要瓶颈。

2. **范围查询效率较低**
    * **缺乏叶子节点链表：** B 树的叶子节点之间没有像 B+ 树那样的链表连接。
    * **需要中序遍历：** 进行范围查询（如 WHERE value BETWEEN X AND Y ）时，B 树可能需要通过**中序遍历**的方式，在不同的节点和层级之间频繁地上下跳转，才能找到所有符合条件的数据。这会导致更多的随机磁盘 I/O，效率远低于 B+ 树沿着叶子节点链表进行顺序遍历。

3. **查询性能不稳定**
    * **数据分散存储：** 在 B 树中，数据记录可能存在于树的任何节点（内部节点或叶子节点）。
    * **查找路径长度不一：** 这意味着查找某个键时，查询操作可能在不同的层级终止。例如，如果目标数据位于靠近根节点的内部节点，查询路径会很短；如果数据位于叶子节点，路径会更长。这种**查找路径长度的不一致性**导致了查询性能的波动，难以保证稳定的查询时间。

4. **不利于全表扫描或顺序访问**
    * **无序存储：** 虽然 B 树的每个节点内部键值有序，但整体上数据记录在磁盘上的物理位置不一定是完全顺序的。
    * **复杂遍历：** 如果需要进行全表扫描（逻辑上的所有数据），B 树的遍历会比较复杂，可能需要多次随机 I/O 来读取分散在各处的节点，效率低于 B+ 树直接遍历叶子节点链表。

## MySQL 日志类型比较

---

MySQL 中有三种重要的日志：undo log、redo log 和 binlog 。它们各自扮演着不同的角色，共同保障了 MySQL 数据库的 ACID 特性（原子性、一致性、隔离性、持久性）以及高可用性（如主从复制和数据恢复）。

以下是它们的用途：

### 1. **Undo Log (回滚日志)**

* **所属层级：** InnoDB 存储引擎层。
* **主要作用：**
    * **事务回滚（原子性）**：当事务执行 `ROLLBACK` 操作，或者事务因错误（如死锁、唯一键冲突）而终止时，`undo log` 记录了数据修改前的状态（“before image”），允许 MySQL 将数据恢复到事务开始前的样子，从而保证事务的**原子性**。
    * **多版本并发控制（MVCC）**：`undo log` 是 InnoDB 实现 MVCC 的关键。它为每条修改的记录保留了多个历史版本。当一个事务进行快照读（Snapshot Read）时，它会根据其自身的 `Read View` 信息，顺着 `undo log` 维护的版本链找到符合其可见性的历史数据版本，从而实现读写不阻塞，保证事务的**隔离性**。
    * **数据恢复（部分作用）**：在崩溃恢复时，`undo log` 与 `redo log` 配合，用于回滚未提交的事务，确保数据库最终处于一致状态。

### 2. **Redo Log (重做日志)**

* **所属层级：** InnoDB 存储引擎层。
* **主要作用：**
    * **崩溃恢复（持久性）**：`redo log` 记录了数据页的物理修改（“after image”），即“某数据页的某个偏移量从 X 变成了 Y”。它是为了保证事务的**持久性**。当事务提交时，MySQL 会首先将数据页的修改写入内存中的 `Buffer Pool`，然后将这些修改对应的 `redo log` 记录写入 `redo log buffer`，并最终刷写到磁盘上的 `redo log file`。即使数据页还没有刷写到磁盘（“脏页”），如果系统发生崩溃，在重启后，MySQL 可以根据 `redo log` 重新执行已提交事务的修改操作，将数据恢复到崩溃前的状态，从而确保已提交的数据不会丢失。
    * **减少磁盘随机 I/O**：`redo log` 采用**顺序写入**的方式，性能远高于直接将修改后的数据页随机写入磁盘文件。通过先写 `redo log` 再定期刷写数据页的策略（WAL - Write-Ahead Logging），大大提升了写操作的性能。

### 3. **Binlog (二进制日志)**

* **所属层级：** MySQL Server 层（独立于存储引擎）。
* **主要作用：**
    * **数据复制（主从同步）**：`binlog` 记录了所有对 MySQL 数据库的修改操作，包括数据定义语言（DDL）和数据操作语言（DML）。在主从复制架构中，主库会将 `binlog` 发送给从库，从库通过回放这些日志来保持与主库的数据同步。
    * **时间点恢复（Point-In-Time Recovery）**：当数据库发生意外数据丢失或损坏时（如误操作、数据被清空），可以利用完整的备份，然后结合备份之后的 `binlog` 来将数据库恢复到指定的时间点，避免数据损失。
    * **审计**：`binlog` 记录了数据库的所有修改操作，可以用于审计数据库活动，追踪数据变更。

### 总结三者关系：

* **`undo log`**：用于**回滚**（“undo”）事务，保证原子性，并支持 MVCC。
* **`redo log`**：用于**重做**（“redo”）已提交事务的修改，保证持久性，提升崩溃恢复速度和写入性能。
* **`binlog`**：用于**数据复制**和**时间点恢复**，是 MySQL 服务器层面的逻辑日志。

`undo log` 和 `redo log` 是 InnoDB 存储引擎特有的，用于保障事务的 ACID 特性；而 `binlog` 是 MySQL 服务器层面的，不区分存储引擎，主要用于数据同步和备份恢复。


## 主从复制

MySQL 的主从复制（Master-Slave Replication）是实现数据库高可用性、读写分离、数据备份和灾难恢复的关键技术。其核心思想是：一台 MySQL 服务器（**主库 Master**）的 DDL 和 DML 操作会实时地同步到一台或多台其他 MySQL 服务器（**从库 Slave**）上，从而使主从数据保持一致。

### 主从复制的原理流程

MySQL 主从复制的整个过程主要涉及到三个线程：一个在主库（Binlog Dump Thread），两个在从库（I/O Thread 和 SQL Thread）。

1.  **主库（Master）记录二进制日志 (Binlog)**
    * 主库上的任何数据修改操作（DDL, DML）都会被记录到其**二进制日志（Binlog）**中。
    * Binlog 中记录的是逻辑事件，描述了数据是如何被修改的（例如：`UPDATE table SET col=val WHERE id=X` 或者直接记录行变更）。
    * 主库的 Binlog 会持续写入新的事件。

2.  **主库（Master）的 Binlog Dump Thread (日志转储线程)**
    * 当从库连接到主库并请求复制时，主库会启动一个专门的 `Binlog Dump Thread`。
    * 这个线程会读取主库的 Binlog，并将 Binlog 事件发送给从库。
    * 如果从库是首次连接或落后较多，主库会从从库指定的 Binlog 文件和位置开始发送；否则，它会实时地将新的 Binlog 事件推送给从库。

3.  **从库（Slave）的 I/O Thread (I/O 线程)**
    * 从库上有一个 `I/O Thread`。它连接到主库，并请求主库的 `Binlog Dump Thread` 发送 Binlog 事件。
    * `I/O Thread` 接收到主库发送过来的 Binlog 事件后，会将其**追加写入**到从库本地的一个文件中，这个文件称为**中继日志（Relay Log）**。
    * 从库会记录当前已经读取到主库 Binlog 的位置（文件名和偏移量），以便下次继续请求。

4.  **从库（Slave）的 SQL Thread (SQL 线程)**
    * 从库上还有一个 `SQL Thread`。它会顺序读取从库本地的**中继日志（Relay Log）**中的事件。
    * `SQL Thread` 会解析这些 Binlog 事件，并**在从库上重新执行（回放）**这些事件所代表的 SQL 操作。
    * 通过回放这些操作，从库的数据就能够与主库保持一致。
    * 从库会记录当前已经执行到中继日志的哪个位置，以及对应的主库 Binlog 的位置。

### 主从复制的配置

配置主从复制通常涉及以下几个关键步骤：

1.  **主库配置：**
    * 在 `my.cnf` 或 `my.ini` 中启用 Binlog (`log-bin` 选项)。
    * 设置唯一的 `server-id`。
    * （可选）设置 Binlog 格式 (`binlog_format=ROW/STATEMENT/MIXED`)，推荐 `ROW`。
    * 重启 MySQL 服务。
    * 创建用于复制的用户，并授予 `REPLICATION SLAVE` 权限。
    * 记录当前主库的 Binlog 文件名和位置（通过 `SHOW MASTER STATUS;` 命令）。

2.  **从库配置：**
    * 在 `my.cnf` 或 `my.ini` 中设置唯一的 `server-id` (必须与主库及其他从库不同)。
    * （可选）配置 `relay-log`。
    * 重启 MySQL 服务。
    * 使用 `CHANGE MASTER TO` 命令配置主库连接信息、复制用户凭证以及复制起始的 Binlog 文件名和位置。
    * 启动从库复制进程 (`START SLAVE;`)。

3.  **数据初始化：**
    * 在设置复制之前，通常需要对从库进行一次完整的数据初始化（例如，从主库导出数据并导入到从库），以确保从库的数据状态与主库开始复制时的 Binlog 位置相匹配。

### 主从复制的优点

* **读写分离：** 主库处理写操作，从库处理读操作，减轻主库压力，提高并发能力。
* **高可用性：** 当主库发生故障时，可以将一个从库提升为新的主库，保证服务的持续可用性。
* **数据备份：** 从库本身就是一份实时的数据副本。
* **灾难恢复：** 利用主从复制，可以在主库完全损坏的情况下，快速恢复数据。
* **数据分析：** 在从库上进行耗时的报表查询或数据分析，不影响主库的在线服务性能。
